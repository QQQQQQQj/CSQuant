## 1. 产品概述

**一句话定位：CSQuant 是面向个人投资者的 CS2/CSGO 饰品量化投研与库存管理系统，不是查价网站。**

它以单用户自有库存为起点，构建「库存估值 → 大盘情绪判断 → 单品量化评分 → 买卖信号 → 历史回测验证 → 人工执行」的完整投研闭环，最终回答"现在该 BUY、HOLD 还是 SELL、依据是什么、这个策略历史上是否真的有效"。

核心边界：

- 行情数据源：CSQAQ 为主源、SteamDT 为辅源、Steam 官方低频校验；BUFF/悠悠有品**不直连**，其价格经 SteamDT/CSQAQ 间接进入系统。
- 交易执行：系统只产出信号与建议，**执行保持人工确认**，不做任何自动下单/出售。
- 技术基线：Python 3.11+ 单语言；V1 单机单进程 + APScheduler + SQLite(WAL) + Streamlit Dashboard；vectorbt 独立 venv 做回测；httpx 异步采集；pydantic v2 校验；全部配置入 `.env`。

版本路线（详见第 4 节 FR 的"所属版本"列）：

| 版本 | 范围摘要 |
|---|---|
| V1 | 元数据 + ID 映射 + Steam 库存同步 + 三源 Provider + 估值/KPI + Portfolio Dashboard + 基础行情存储 |
| V2 | 大盘指数 + MarketScore + 市场宽度 + 流动性 + 供需指标 |
| V3 | ItemScore + BUY/HOLD/SELL + 风险等级 + 信号追溯 + Signal Dashboard + 告警 |
| V4 | VectorBT 回测 + 参数搜索 + 大盘 Benchmark |
| V5 | Event Agent + LLM 信号解释 + Portfolio Manager + 建议仓位 |

## 2. 目标用户与使用场景

### 2.1 目标用户

- **唯一用户画像**：持有数十至数百件 CS2 饰品的个人投资者/投研者（即系统所有者本人），单用户、无多租户、无账号体系。
- 用户具备基本投资概念（成本、盈亏、回撤、胜率），但不依赖本系统做毫秒级交易决策。

### 2.2 典型使用场景

**场景 A：每日例行投研（主路径，约 5 分钟）**

1. 打开 Dashboard「市场大盘」页：看 MarketScore（0~100）与五档情绪（极度恐慌/偏空/震荡/偏多/极度贪婪）、涨跌家数比、成交活跃度；
2. 打开「总资产与盈亏」页：看总估值、总浮盈、当日变化、净值曲线；
3. 打开「买卖信号」页：筛选今日 BUY/SELL 信号，逐条查看评分、置信度、风险等级与理由；
4. 对认可的信号，**跳转到第三方平台人工下单**，回系统手工登记成交（更新成本）。

**场景 B：买入前论证（约 10 分钟）**

用「饰品筛选器」按品类/流动性/评分筛出候选 → 进「单品详情」看价格历史与因子分解 → 进「回测」页验证该信号规则历史表现 → 决定是否买入。

**场景 C：异常处置**

收到"数据源故障"或"价格异动"告警 → 在「数据源状态」页确认主备切换是否生效 → 判断是否需要暂停采信当前行情。

## 3. 产品必须回答的 11 个核心问题

直接引用指示文档第 19 节。系统所有功能以完整回答以下问题为最终验收目标（括号内为主要承载功能/页面）：

1. **我现在有哪些饰品？**（FR-1 我的库存）
2. **它们涨了还是跌了？**（FR-3 库存/单品盈亏）
3. **我的总资产变化如何？**（FR-4 净值曲线、总资产页）
4. **现在整个 CS 饰品市场是牛、熊还是震荡？**（FR-6 MarketScore、市场大盘页）
5. **哪些饰品正在变强？**（FR-7 ItemScore、筛选器）
6. **哪些饰品正在走弱？**（FR-7 ItemScore、筛选器）
7. **为什么？**（FR-9 信号解释与因子分解）
8. **现在应该 BUY、HOLD 还是 SELL？**（FR-8 信号）
9. **这个信号的依据是什么？**（FR-9 信号追溯：当时数据快照 + 因子快照 + 模型版本）
10. **这个策略历史上真的有效吗？**（FR-10 回测：收益/回撤/Sharpe/胜率 + 大盘基准对比）
11. **我应该承担多大风险？**（FR-8 风险等级、V5 建议仓位）

## 4. 功能需求（FR 列表）

优先级定义：P0 = V1 必须上线否则产品不成立；P1 = 版本内核心；P2 = 版本内可延后。

### FR-1 Steam 库存同步与手工补录（P0 · V1）

- **描述**：通过 Steam 官方接口同步本人 CS2 库存，经 ID 映射识别为 item_master 记录；同步失败或未映射的饰品支持手工补录。
- **输入**：`.env` 中的 `STEAM_API_KEY`、`STEAM_ID64`；触发方式（手动按钮 / 每日 1 次定时）；手工补录表单（market_hash_name 搜索词、数量、备注）。
- **输出**：`portfolio_position`（item_uuid、asset_id、quantity、状态 active/removed）；同步报告（新增/移除/未识别数量）；未识别饰品待办列表。
- **验收**：同步结果与 Steam 实际库存一致率 100%（资产数对账）；按 asset_id 幂等去重，重复同步不产生重复持仓；已售出饰品牌置 removed 而非物理删除；未映射饰品不丢弃，进入待办并可手工指定 item_uuid。

### FR-2 买入成本管理（P0 · V1）

- **描述**：登记与维护每件持仓的买入成本，支持修改留痕与部分卖出。
- **输入**：position_id、buy_price（币种 CNY/USD，必填币种字段）、buy_time、quantity、fee；CSV 批量导入（列：market_hash_name, buy_price, buy_time, quantity, fee）；部分卖出数量。
- **输出**：cost_basis（加权平均成本）；成本变更审计日志（旧值/新值/时间/操作人备注）；部分卖出后的剩余成本与已实现盈亏记录。
- **验收**：成本可多次修改且全量留痕；缺失成本的持仓在估值页明确标记"成本缺失"而不是按 0 计算盈亏；部分卖出按加权平均口径结转成本（口径写入文档，可切换 FIFO 为 P2）。

### FR-3 实时估值与盈亏 KPI（P0 · V1）

- **描述**：基于 Provider 最新报价对全部持仓估值，输出单品与组合两层 KPI。
- **输入**：持仓（quantity、cost_basis）；最新行情快照（sell_price、buy_price、source、platform、source_update_time、data_quality）；估值口径配置（默认主源最低在售价，可切换求购价保守口径）。
- **输出**：单品级：current_price、current_value、unrealized_pnl、return_rate、staleness 标记；组合级：total_value、total_cost、total_unrealized_pnl、total_return_rate、day_change、持仓件数。
- **验收**：KPI 与抽样手算结果一致；报价超过新鲜度阈值（见 NFR-2）的持仓显示 stale 标记且不计入"实时"口径汇总；缺失报价不计为 0。

### FR-4 净值曲线（P0 · V1）

- **描述**：定时固化组合净值快照，绘制历史净值与收益率曲线。
- **输入**：每个采集周期结束时的持仓 × 行情快照；成本变更事件。
- **输出**：`portfolio_nav_snapshot`（timestamp、total_value、total_cost、unrealized_pnl、return_rate）；可缩放净值曲线（叠加成本线）；区间统计（区间收益率、区间最大回撤）。
- **验收**：每自然日至少 1 个快照；任意历史区间可回溯；成本变更当日的收益率计算不受注资/撤资影响（用变更前快照分段，口径写入文档）。

### FR-5 行情采集与存储（P0 · V1）

- **描述**：经统一 Provider/Adapter 层从 CSQAQ（主）、SteamDT（辅）、Steam 官方（低频校验）采集行情并时序落库；BUFF/悠悠价格以字段形式随主辅源入库。
- **输入**：watchlist（item_uuid 列表 + 分层等级 L1/L2/L3）；Provider 配置（API Key、限频 1 req/s、超时、重试次数）；调度策略（L1 5min / L2 15min / L3 30–60min / Steam 校验 ≤24h）。
- **输出**：`market_snapshot` 时序记录（timestamp、item_uuid、source、platform、sell_price、buy_price、sell_count、buy_count、volume、currency、source_update_time、data_quality）；采集运行日志（成功/失败/重试/切换）。
- **验收**：每条记录必带 source 与 data_quality（ok/stale/degraded/anomaly），覆盖率 100%；主源失败自动降级备源并记日志；缺失字段显式为 null 而非 0；接口字段映射在 DATA_SOURCE_SPEC 中逐字段登记，未确认字段标「待验证」。

### FR-6 大盘情绪 MarketScore（P1 · V2）

- **描述**：用可解释数值指标计算 0~100 大盘情绪分与五档状态，不依赖 LLM。
- **输入**：大盘指数趋势（权重初始 25%）、市场宽度/涨跌家数比（20%）、成交与流动性（20%）、求购/在售供需（15%）、跨平台价格一致性（10%）、事件因子（10%，V5 前默认为中性值）。
- **输出**：`market_index`（timestamp、market_score、market_regime 五档、各分项分数、breadth、volume_score、liquidity_score）；分项缺失时的降级标记。
- **验收**：五档阈值（0-20/20-40/40-60/60-80/80-100）与六项权重均为配置项，修改产生新配置版本；每个分项分数可追溯到当日原始统计数据；任一因子缺失时降级计算并标记，不允许静默按满分处理。

### FR-7 单品评分 ItemScore（P1 · V3）

- **描述**：对每件饰品计算 0~100 量化评分，因子权重初始值取自指示文档第 8 节，须经回测校准。
- **输入**：趋势（20%）、相对大盘强弱（15%）、供需（20%）、成交量（15%）、流动性（10%）、跨平台一致性（10%）、估值（5%）、事件（5%，V5 前中性）；每个因子为确定性代码计算的数值。
- **输出**：`item_score` 记录（timestamp、item_uuid、item_score、各因子分项值、缺失因子列表、权重配置版本）。
- **验收**：因子计算公式逐一文档化且单元测试覆盖；权重改动产生新版本号并随评分落库；因子缺失按规则降级（剔除该因子并归一化剩余权重），缺失清单可见。

### FR-8 BUY/HOLD/SELL 信号（P1 · V3）

- **描述**：由 ItemScore + MarketScore 按阈值规则生成三档信号，附置信度与风险等级。
- **输入**：item_score、market_score、阈值配置（示例：≥75 BUY 候选、45~75 HOLD、<45 SELL 候选，**阈值必须回测确认后生效**）；流动性分档（用于风险等级）。
- **输出**：`signal`（timestamp、item_uuid、signal、item_score、market_score、confidence、risk_level（低/中/高）、reason_json、suggested_position（V5 前为 null）、model_version）。
- **验收**：信号 100% 落库不覆盖；信号生成逻辑与回测引擎复用同一份策略代码（单一实现）；risk_level 由流动性分档 + Spread + 数据质量推导，推导规则文档化。

### FR-9 信号解释与追溯（P1 · V3；LLM 解释 V5）

- **描述**：任意历史信号可一键还原"当时的依据"。
- **输入**：signal_id。
- **输出**：该信号对应的因子分项快照、当时最近一条行情快照（含 source_update_time）、当时 MarketScore 与配置版本、reason_json 结构化理由（如"trend=+12 分：7 日涨幅 8.3% 超大盘 5.1pct"）。
- **验收**：任意 signal_id 可在 3 秒内呈现完整快照链；reason_json 每条理由绑定具体因子数值；V5 的 LLM 自然语言解释为独立开关，仅引用已有数值，不作为任何数值计算的输入。

### FR-10 历史回测（P1 · V4）

- **描述**：用 vectorbt（独立 venv、版本钉死）对信号规则做历史验证，含 CS 饰品特殊执行模型。
- **输入**：策略/信号规则及版本、回测区间、初始资金、分平台手续费率、滑点模型、bid-ask 执行价模型、流动性过滤参数（最低成交量/最大持仓天数假设）、基准（大盘指数）。
- **输出**：`backtest_result`（strategy_name、strategy_version、start/end_date、total_return、annualized_return、max_drawdown、sharpe、win_rate、profit_factor、trade_count、turnover、fee_cost、slippage_cost、benchmark_return）+ 可复现报告（含全部输入参数快照）。
- **验收**：同一参数集重跑结果完全一致（可复现）；禁止使用最低挂售价直接作为成交价（须经执行价模型修正）；强制 point-in-time 数据切片防未来数据泄漏，泄漏检查列入测试；结果必含与大盘基准的对比。

### FR-11 饰品筛选器（P2 · V2）

- **描述**：多条件筛选饰品并联动其他页面。
- **输入**：category、weapon、wear、rarity、collection、价格区间、成交量/流动性阈值、ItemScore 区间、信号类型（V3 后）。
- **输出**：命中列表（每行：名称、品类、最新价、1d/7d/30d 涨跌幅、成交量、ItemScore、当前信号）；操作：加入 watchlist（指定 L1/L2/L3）、跳转单品详情、导出 CSV。
- **验收**：筛选条件可组合保存为预设；结果列数据均带数据时间戳。

### FR-12 数据源健康监控（P1 · V1 起持续）

- **描述**：对三个 Provider 做健康探针与运行统计，支撑主备切换决策。
- **输入**：定时 `health_check()` 探针结果；每次采集调用的成功率、延迟、限频余量（若接口返回，待验证）。
- **输出**：provider_status（source、状态 ok/degraded/down、最近成功时间、连续失败次数、24h 成功率、平均延迟）；数据源状态页；故障事件日志。
- **验收**：主源连续失败达到阈值（默认 3 次）自动切备源并记录；故障/恢复均产生告警事件；状态页数据延迟 ≤1 个采集周期。

### FR-13 系统设置（P2 · V1）

- **描述**：集中管理配置，密钥只走 `.env`。
- **输入**：API Keys（CSQAQ/SteamDT/Steam，仅 .env 编辑，页面只读掩码展示）；采集频率与分层配额；watchlist 管理；MarketScore/ItemScore 权重与阈值；估值口径；币种。
- **输出**：生效配置快照 + 配置版本号（config_version，与 signal.model_version 关联落库）。
- **验收**：密钥不写入数据库、不明文出现在任何页面与日志；权重/阈值类配置变更产生新版本号且可追溯；非法配置（权重和 ≠100%）保存时校验拒绝。

### FR-14 告警（P2 · V3）

- **描述**：对关键事件进行本地通知。
- **输入**：告警规则（新 BUY/SELL 信号、持仓单日涨跌超 X%、MarketScore 跨档、数据源故障/恢复、报价异常标记）；通知渠道（Streamlit 页面内通知为 V1 基线；邮件/Webhook 待验证后置）。
- **输出**：alert_event（timestamp、rule_id、event_type、关联对象 signal_id/item_uuid、触发数据快照摘要、通知状态）。
- **验收**：同类告警可配置静默期去重；每条告警关联触发它的数据快照；告警历史可查询。

## 5. 非功能需求（NFR）

### NFR-1 性能与采集可行性论证

- **问题**：500 件自选、5 分钟级采集周期、限频 1 req/s 是否可行？
- **单条轮询模式**：500 件 × 1 req/s = 500 秒 ≈ 8.3 分钟 > 5 分钟周期，**纯单条轮询不可行**。
- **可行路径（按优先级）**：
  1. **批量报价接口**：CSQAQ/SteamDT 若支持单请求多饰品批量报价（批量上限「待验证」，假设 ≥50 件/次），则 500 件仅需 ≤10 次请求 ≈ 10 秒，5 分钟级完全可行——这是首选方案，接口能力须在 DATA_SOURCE_SPEC 中实测确认；
  2. **分层调度兜底**：无批量接口时，L1（≤60 件，5min，每周期 60 请求）+ L2（≤240 件，15min）+ L3（其余，30–60min），则 L1 层 5 分钟新鲜度可行（60s < 300s），全量 500 件 5 分钟级**不可行**，须在产品上明确该预期；
  3. httpx 异步客户端 + 令牌桶限频器（1 req/s）+ 指数退避重试（≤3 次）。
- **存储写入负载**：500 件 × 最高 288 周期/日 ≈ 14.4 万行/日上限；SQLite(WAL) 单写多读可承受；读侧 Dashboard 查询须走索引（item_uuid+timestamp）。
- **Dashboard 响应**：首屏 KPI 查询 ≤3 秒（500 件规模，读取预聚合结果而非实时计算）。

### NFR-2 数据新鲜度指标

| 数据 | 新鲜度目标 | 超期处置 |
|---|---|---|
| L1 自选行情 | ≤5 分钟 | 标记 stale，估值口径降级 |
| L2 行情 | ≤15 分钟 | 标记 stale |
| L3 行情 | ≤60 分钟 | 标记 stale |
| Steam 官方校验 | ≤24 小时 | 仅告警，不阻塞 |
| 元数据/ID 映射 | ≤24 小时 | 后台重试 |
| 净值快照 | 每日 ≥1 条 | 补采并标记 |

### NFR-3 可用性

- 采集进程与 Dashboard 解耦：Dashboard 崩溃不影响采集与落库；采集进程异常退出后由启动脚本拉起（可选 systemd/计划任务）。
- 单源故障不导致系统失效：主源 down 时备源接管，信号页展示"数据降级"横幅。

### NFR-4 可审计性

- **每个信号 100% 可追溯**：signal_id → 因子快照 + 行情快照（含 source_update_time）+ MarketScore + 权重/阈值配置版本 + model_version，五要素缺一不可。
- 成本变更、配置变更、主备切换全部留痕（谁/何时/旧值/新值）。
- 回测报告含完整输入参数快照，同参重跑结果一致。

### NFR-5 数据质量纪律

- 缺失数据显式 null，**禁止默认填 0**；异常行情（如瞬时价格偏离超过阈值）打 `data_quality=anomaly` 标记但不擅自清洗原始值；所有时间统一时区（UTC 存储，展示转本地）；所有价格必带币种字段。

### NFR-6 合规

- 仅限个人非商用投研用途；CSQAQ 存在严禁商用条款、SteamDT 限时免费政策不确定，架构上必须支持任一源被移除后系统降级运行；API Key 仅存本地 `.env` 且不提交 Git；vectorbt 为 Commons Clause 许可，自用合规，商业化需重新评估。

## 6. 用户故事

**US-1（库存同步）**：Given 我已配置 STEAM_API_KEY 与 STEAM_ID64，When 我在「我的库存」点击"同步库存"，Then 系统列出全部持仓（名称/磨损/图片/数量），并给出"新增 X、移除 Y、未识别 Z"的同步报告，未识别饰品进入待办列表。

**US-2（每日大盘）**：Given 系统已完成当日采集与 MarketScore 计算，When 我打开「市场大盘」页，Then 我看到 MarketScore 数值、五档情绪标签、涨跌家数比、成交活跃度及各分项分数，且每个分项可点开查看原始统计。

**US-3（盈亏查看）**：Given 我的持仓均有成本且行情在新鲜度阈值内，When 我打开「总资产与盈亏」页，Then 我看到总估值、总浮盈、总收益率、当日变化与净值曲线；When 某件饰品报价过期，Then 该饰品显示 stale 标记且不计入"实时"汇总。

**US-4（信号决策）**：Given 系统已生成今日信号，When 我在「买卖信号」页点击某条 BUY 信号，Then 我看到 ItemScore 各因子分项、当时行情快照、MarketScore、置信度、风险等级与逐条结构化理由，且可确认其 model_version。

**US-5（回测验证）**：Given 我配置了一套信号阈值，When 我在「回测」页选择该策略版本与历史区间并运行，Then 我得到含总收益/最大回撤/Sharpe/胜率/换手/费后收益及大盘基准对比的报告；When 我用相同参数再次运行，Then 结果完全一致。

**US-6（数据源故障）**：Given CSQAQ 主源连续 3 次调用失败，When 下一个采集周期到来，Then 系统自动切换 SteamDT 备源、在「数据源状态」页将主源标为 down、产生一条告警事件，信号页出现"数据降级"提示。

**US-7（手工补录）**：Given 我在第三方平台线下买入一件饰品，When 我在「我的库存」使用手工补录搜索 market_hash_name 并录入成本，Then 该饰品以 active 状态加入持仓并立即参与估值，操作计入审计日志。

## 9. 范围边界（明确不做清单）

**全版本不做**：

1. 全自动下单 / 自动出售 / 自动确认 Steam Guard —— 执行永远人工确认；
2. 账号批量操作、高频抢单、高频套利机器人；
3. BUFF / 悠悠有品直连采集（仅经主辅源间接获取）；
4. 多用户、账号体系、SaaS 化；
5. 把 LLM 用于价格、收益率、技术指标等任何数值计算。

**V1 明确不做**（指示文档第 11 节）：强化学习、大规模深度学习价格预测、复杂微服务拆分、自研回测引擎（V4 用 vectorbt 薄封装）、LangGraph/Agent 编排（V5 引入）、重前端（V1 Streamlit）。

**数据相关不做**：不抓取 Steam 页面作为核心数据源（仅官方接口低频校验，非正式解析方案一律标"不稳定"）；不在 V1 接入 SteamTradingSiteTracker-Data 大型历史仓库（V4 按需获取）。
